# Secrets

**You want to:** check that a Secret exists and has the right keys, read one value, or change it.

Seeing that a Secret exists, reading a value and changing it are separate permissions:

| Permission | What you get |
|---|---|
| `secrets:list` | the Secrets tab: name, type, number of keys, age |
| `secrets:get` | **Keys**: type, labels, annotations, key names and sizes, no values |
| `secrets:reveal` | **Show** on one key: that key's value, with copy and hide |
| `secrets:edit` | **YAML**: the whole Secret in the editor, values included |

## Read one value

**Keys** opens the Secret without its values. **Show** next to a key fetches that one value; **Hide** or closing the
window forgets it.

<Screenshot id="secret-reveal" alt="Secret storefront-db: the note that every value viewed is written to the audit log, the password key revealed, the username key still hidden" />

Every value you show is written to the audit log (`secret.reveal`, with the key's **name**, never its value). Values
never travel with the list or with **Keys**.

## Change it

With `secrets:edit`, **YAML** opens the editor ([YAML view and edit](/user-guide/yaml)). Text values appear readable
under `stringData`, so you edit plain text instead of base64; binary values stay base64 under `data`. Removing a key
from the YAML deletes it. Opening the YAML is audited (`secret.view_yaml`), and so is applying it (`secret.apply`).

:::info[Can't see it or can't do it?]
- **No Secrets tab**: you don't hold `secrets:list` here, or the admin switched Secrets off for everyone.
- **No Show button**: you hold `secrets:get` but not `secrets:reveal`.
- **No YAML button on a Secret**: opening it needs `secrets:edit`; `get` or `reveal` is not enough, because the YAML
  holds every value.
- **"ServiceAccount is not allowed to read secrets"**: the cluster connection can't read Secrets; ask your admin.
:::
